# 0006. Standalone, one-click diagnostics suite with a built-in calibration gate

## Status

Accepted

Revises the operating model of the harness built in ADR 0004 and extended in
ADR 0005. Does not reopen either — the timeline origin, arming, and Offset
decisions all stand.

## Context

The Diagnostics panel as built lets a user manually trigger three
independent actions — Synthetic Sync Scenario (Mode B), Acoustic Loopback
(Mode A), and a standalone "Write Report" — each configured separately, each
writing its own timestamped report file. Using it correctly requires knowing
and following discipline that lives only in `docs/testing-sync.md`: run Mode
B before Mode A, run a calibration pass before trusting a zero-error result,
correlate reports by `sessionId` to know which belong to one test session.
Nothing in the code enforces any of this — a user can read a clean report
that was never calibrated, or read a Mode A report without ever having
validated Mode B first, and nothing says so.

Two concrete problems surfaced this:

**A Guide-shaped hole.** Mode B and Mode A each construct their own beat
timing independently — `runSyntheticScenario` builds a disconnected
`RecordingEngine`/Project with `guide: null` and never calls
`importGuide()`; the expected-beat-times array is computed from
`tempoBpm`/`beatCount` math, not from anything actually scheduled or played.
Mode A separately plays "the synthetic click" through speakers. Nothing
connects the two, and nothing connects either to a real Guide the user might
generate in the main app — a user who clicks "Generate Guide" before running
diagnostics gets no error and no effect; the click is silently inert for
diagnostics purposes. This was not a deliberate scope cut, just never
decided.

**A silent-looking first Take.** A user running several synthetic Takes in a
row reported hearing count-in, silence, count-in, audible beeps, count-in,
audible beeps — as if the first Take were failing. It isn't:
`SyntheticCaptureAdapter.stopCapture` always renders a full beep track
regardless of Take order. What's silent is Monitor Mix playback in
`RecordingEngine.recordTake`, which only plays back *previously recorded*
Tracks — on Take 1 there are none. This is correct behavior for the current
model, but it's confusing, and it goes away as a side effect of the fix
below: once a Metronome is a real Guide, audible in Monitor Mix from Take 1
onward, there is always something to hear.

Both problems trace to the same root: diagnostics compares captured audio
against an *implicit*, separately-computed notion of "where the beats should
be" rather than against something real that was actually scheduled and
played — the same gap CONTEXT.md's Guide concept exists to close for normal
recording, just never extended to diagnostics.

## Decision

**Guide gains a second source: Metronome.** CONTEXT.md's Guide definition
widens from "imported reference audio" to reference audio from either
source — imported by the user, or a **Metronome** generated by the tool.
Both fill the identical structural role (audible in Monitor Mix, anchors
the Project timeline's t=0, defines the beat grid); they differ only in
provenance. Metronome is deliberately simple: one constant tempo and time
signature for its whole duration, no mid-Guide tempo or meter changes — that
flexibility (which "click track" as a term would imply) is explicitly not
supported yet. This was chosen over minting a second, disconnected term
because a musician distinguishes "the reference recording I brought in" from
"the click the tool gives me" by role and origin, not by any structural
difference the model needs to track separately.

**Diagnostics becomes a standalone flow with an ephemeral Project.**
Running diagnostics no longer requires creating or opening a real Project.
The suite spins up its own ephemeral Project, generates a Metronome into it
once, and both Mode B and Mode A capture against that same Metronome's beat
grid — replacing the current independent, disconnected timing math in each
mode. This also resolves the silent-first-Take confusion for free: the
Metronome is audible in Monitor Mix from the first Take, because it isn't
waiting on a prior Take to exist.

**Calibration becomes a hard gate, not documentation.** The suite runs a
calibration pass first — inject a known nonzero latency, confirm the
harness reports approximately that value — before running Mode B or Mode A
for real. If calibration fails, the suite aborts before running either mode;
no report is written that could be mistaken for a real measurement. This
moves `docs/testing-sync.md`'s "Calibrate before you trust a clean result"
section from a discipline the reader must remember to a property the report
now guarantees.

**One button, fixed defaults, single unified report.** "Run Full
Diagnostics" runs calibration → Mode B → Mode A end to end with fixed,
sensible scenario config (Track count, tempo, beats per bar, beat count) —
no setup form on the primary path. All three phases write into one report
file per suite run, replacing the current one-file-per-manual-action layout;
a reader (human or the `read-diagnostics-report` skill) no longer needs to
correlate files by `sessionId`/timestamp proximity to reconstruct that they
belong to one session.

**Manual per-phase controls survive, demoted.** The existing standalone
Mode B, Mode A, and Write Report actions — plus the config knobs the one-click
path no longer exposes — remain reachable behind an advanced/disclosure
area, for debugging the harness itself (e.g. iterating on the onset detector
without paying for a full suite run each time).

## Consequences

- `CONTEXT.md`'s Guide definition changes (already applied): two sources,
  same role. Nothing downstream of "Guide" as a concept (Monitor Mix,
  Mixdown exclusion, t=0 anchoring) needed to change — only where the audio
  comes from.
- `docs/testing-sync.md` needs a substantial rewrite: the Mode-B-before-Mode-A
  ordering and the calibration discipline move from reader responsibility to
  suite-enforced behavior; the report-reading sections need updating for a
  single unified report shape instead of one-report-per-action.
- The `read-diagnostics-report` skill's guidance to "sort by filename to find
  the newest, correlate by sessionId" simplifies once one suite run produces
  one file — worth revisiting once the new report shape lands.
- This is new engine surface: an ephemeral-Project code path that today's
  `RecordingEngine` doesn't have (Mode B currently builds one disconnected,
  throwaway `RecordingEngine` per run; making that the *only* path, shared
  by both modes, and wiring a generated Metronome into it, is real
  implementation work, not a config change).
- A user who wants to diagnose sync against a *specific imported* Guide file
  (not a Metronome) has no path to do that after this decision — diagnostics
  is Metronome-only by design. If that need arises later, it's new scope,
  not something this ADR left half-done.
- Old reports in `diagnostics/` (one file per manual action, `project.guide`
  always null) are not migrated or reinterpreted by this decision; they
  remain readable as what they were, under the old model.
